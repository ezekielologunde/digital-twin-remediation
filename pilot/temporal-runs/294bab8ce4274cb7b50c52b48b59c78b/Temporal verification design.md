# Temporal verification development experiment

Written before launch, 4 October 2026. This is a bounded manipulation study, not a novelty claim or confirmatory evaluation.

Research question: Can dependency checks that pass before a controlled state change incorrectly approve a later target-only restart, and can a final refresh detect that change?

Hypotheses: With no additional fault, all three evidence policies approve and the eight-second recovery contract is met. A Redis stop before the middle refresh invalidates cached approval but is detected by subsequent checks. A Redis stop after that refresh invalidates both cached and middle-refresh approval, but is detected by the final refresh. These are expected consequences of time-dependent evidence, not a new algorithm.

Six fresh independent instances: one synthetic account block, three fault placements (none, before middle refresh, after middle refresh), crossed with 4 and 8 second delays from middle-refresh completion to final-refresh start. Order is shuffled using seed 20261010. This is a delay manipulation with state-change timing controlled by probe boundaries, not a calibrated evidence-expiry curve. No claims about stochastic failure hazards are supported.

Procedure: Initialize and verify three synthetic records. Stop only the target timeline service. Collect successful cached dependency evidence. Inject the additional Redis stop at its scheduled boundary, if applicable. Collect middle evidence, wait to the assigned deadline, then collect final evidence. Each collection checks Redis, MongoDB and post storage in that fixed order from peer containers. Record monotonic boundaries, seal all three shadow decisions, then start only the verified target container. All policies share the same probe interventions and outcome; six trials are not eighteen independent observations. A delay overshoot above 0.5 seconds fails the manipulation and halts the batch without replacing it.

Outcome: Last two scheduled reads within eight seconds after action decision verify exact known content and creator, with no observed creator mismatch. Verify Redis remains in its injected state and MongoDB remains running after action. Preserve failed attempts, raw commands, configuration, source, predictions, timing and cleanup records. Audit hash integrity and actual event ordering. Report per-condition approvals, incorrect approvals, recovery labels, measured delays and evidence-to-action ages. No p-values or general reliability bounds.

Limits: Final rechecking is not atomic with action; this study deliberately does not inject a new fault after final verification. Sequential probes do not certify a coherent simultaneous state. Fault-command and final-check overhead affect evidence ages, so report actual timing rather than calling the assigned 4/8 seconds action-time age. There is only one instance per cell, existing known fault types, one workload and a fixed probe order. All actions execute even when a policy abstains. This tests availability and content, not security containment. It does not evaluate policy-specific runtime cost or a deployed gate. Success would establish a failure mechanism and a baseline only.
